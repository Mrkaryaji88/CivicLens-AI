# CivicLens AI

**Build for Impact: Reimagining the Future with AI** · Kanpur, Uttar Pradesh pilot concept

CivicLens is a civic issue reporting and operations workflow. It supports a local demo mode and an optional Supabase-backed mode for citizen accounts, shared reports, and admin/staff operations. It is not connected to a municipal government system and is not yet a deployed municipal service.

## Problem and users

Reports about waste, overflowing bins, water leaks, blocked drains and damaged roads are often scattered across channels. The intended users are residents, municipal administrators and field staff. A municipal team must adopt the CivicLens dashboard or authorize an official integration before reports reach its operations.

## Current features

- Responsive React dashboard, complaint search and status filter.
- Report creation with required-field and length validation.
- Optional Supabase email/password signup and login; signup creates citizen accounts only.
- Shared complaint read/write through Supabase when configured, with database RLS controlling access.
- Admin assignment to provisioned staff, staff status workflow, and database status history trigger.
- Browser-local demo mode when Supabase environment values are absent.
- Unique report IDs generated by the database in Supabase mode and within the browser dataset in demo mode.
- Explainable local priority estimate using the proposed 35/25/20/10/10 weighted model.
- SQL foundation for Supabase Auth, PostgreSQL, RLS, assignments, evidence metadata, analysis records, notifications, feedback and audit logs.

Dashboard seed records are illustrative and only used in demo mode. The role selector is available only in demo mode; with Supabase configured, account roles come from `profiles` and RLS enforces access. Supabase setup and SQL have not been verified against the user's live project.

## Architecture

```text
Demo: Browser → React/TypeScript → localStorage

Configured mode:
React client → Supabase Auth → PostgreSQL + Row Level Security
                                      └── Admin/staff operations

Not connected yet: private evidence storage, Gemini/YOLO, municipality systems
```

## Stack

React 18, TypeScript, Vite, Lucide React, CSS, Supabase JS, PostgreSQL/RLS SQL, Vitest. Maps, charts, image upload, notifications, AI functions and server-side municipality integration are not implemented.

## Priority scoring

The documented formula is `severity × .35 + public impact × .25 + location risk × .20 + duration × .10 + evidence confidence × .10`. Inputs are normalized from 0–100 and output is rounded to an integer. Bands are Critical (75–100), High (50–74), Medium (30–49), Low (0–29). The current local fallback estimates factors from the category and description using simple keyword rules; it is neither AI analysis nor an official municipal standard. Confidence remains a separate concept in the planned AI contract. Water leakage needs human inspection.

## Database and security status

`supabase/schema-phase2.sql` defines tables, checks, indexes, citizen profile creation, RLS policies, status history, staff update guard, and an admin-only assignment RPC. New accounts receive the citizen role. Promote admin/staff accounts only from the trusted Supabase SQL editor after those users have signed up; never accept a role from browser metadata. The schema has not been applied to or independently validated against a live Supabase project. It is for a fresh project; inspect the SQL before running it. Storage policies and external government integration are not set up.

## Local development

Requirements: Node.js 24 LTS (or another compatible supported LTS) and npm.

```bash
npm install
npm run dev
npm run build
npm test
```

### Enable the Supabase-backed mode

1. Create a Supabase project.
2. In its SQL Editor, review and run `supabase/schema-phase2.sql` once in the fresh project.
3. Copy the Project URL and **publishable key** from the Supabase dashboard. This browser key is public by design; RLS must protect every table. Never use the Supabase secret/service-role key in this app.
4. Create `.env.local` in the project root (same level as `package.json`):

```dotenv
VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_SB_PUBLISHABLE_KEY
```

5. Restart `npm run dev`, then create a citizen account. If email confirmation is enabled, confirm the email before signing in.
6. To provision an officer, have that person sign up first. In Supabase SQL Editor, look up the account ID and set the role using a trusted operator session:

```sql
select id, email from auth.users where email = 'officer@example.com';
update public.profiles set role = 'admin' where id = 'PASTE-THAT-USER-UUID-HERE';
-- use 'staff' instead of 'admin' for field staff
```

Admin can then assign complaints to those staff accounts. Do not expose a Supabase secret/service-role key in the browser, `.env.local` values must not be committed, and never put Gemini keys in `VITE_` variables. `.env.local` and `.dev.vars*` are ignored by Git.

The client can access complaints only after the migration and RLS policies are applied. No Gemini secret or Gemini server function is currently used.

## Deployment setup (not yet deployed)

Deploy the static Vite build to Cloudflare Pages after GitHub is connected. Set the public `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` build variables there. The Supabase Auth site URL and allowed redirect URLs must include the deployed site. This publishes the app but does not send reports to the government: an authorized municipal operator needs access to the dashboard, or the municipality must approve an official integration. Provider free-tier limits can change; verify current terms before relying on them.

## AI and evidence roadmap

Gemini must be called from a trusted server function, return schema-validated structured JSON, and require human review for uncertain or high-impact cases. No Gemini integration currently exists. YOLO/ONNX weights are not included and no image inference currently executes; select a suitably licensed lightweight model, document its license and provide weights out of repository. Duplicate detection, before/after comparison and map views are not implemented. Never claim repair based only on image analysis.

## Tests and known limitations

Priority scoring tests pass. A production build was checked. Supabase auth, RLS, assignment RPC, status audit trigger and browser submission have not been tested against a live Supabase project; configure one and run an end-to-end test before using real reports. Photo upload, notification delivery, bilingual UI, public dashboard, analytics, AI and municipal system integration remain unimplemented.

## Repository hygiene

Keep a single `main` branch. Exclude `node_modules`, `dist`, `.env*` (except `.env.example`), secrets, datasets and model weights. Check repository size before competition submission and do not claim a live service without verifying it.
